## Get started

```bash
cargo add reqsign --features dropbox
```

```rust
use reqsign::{default_context, dropbox};

// The default chain reads DBXCLI_ACCESS_TOKEN through the context environment.
let ctx = default_context();
let signer = dropbox::default_signer(ctx);

let mut req = http::Request::builder()
    .method(http::Method::POST)
    .uri("https://api.dropboxapi.com/2/users/get_current_account")
    .body(())?
    .into_parts()
    .0;

// Sign in place, then send with the HTTP client you already use.
signer.sign(&mut req, None).await?;
```

The default source is the `DBXCLI_ACCESS_TOKEN` variable documented by the
official `dbxcli` tool. Reqsign does not read `dbxcli` account or team files.
For an explicit access token, use `StaticCredentialProvider`; for long-lived
access, replace the provider with `RefreshCredentialProvider`:

```rust
use reqsign::dropbox::{RefreshCredentialProvider, default_signer};

let ctx = reqsign::default_context();
let provider =
    RefreshCredentialProvider::new("client-id", "client-secret", "refresh-token")?;
let signer = default_signer(ctx).with_credential_provider(provider);
```

The refresh provider sends the client ID and secret in the RFC 6749 form body
and uses Dropbox's fixed token endpoint unless the caller explicitly replaces
it with another trusted HTTPS endpoint. It rejects a successful token response
that omits `expires_in`, because Dropbox access tokens are expected to expire
and an unknown lifetime must not be cached as permanent.

Dropbox uses header authentication only. Signing adds a sensitive
`Authorization: Bearer` header and rejects `expires_in`; it never modifies the
URI or other headers. Refresh-token rotation is serialized per shared provider,
and the access-token cache belongs to `Signer`.
