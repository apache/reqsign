## Get started

```bash
cargo add reqsign --features azure
```

```rust
use reqsign::{azure, default_context};

// Shared key, SAS, or Entra ID (client secrets, workload identity,
// managed identity, Azure CLI) — resolved by the default chain.
let ctx = default_context();
let signer = azure::default_signer(ctx);

let mut req = http::Request::builder()
    .method(http::Method::GET)
    .uri("https://myaccount.blob.core.windows.net/my-container/my-blob")
    .body(())?
    .into_parts()
    .0;

// Sign in place, then send with the HTTP client you already use.
signer.sign(&mut req, None).await?;
```

## Azurite and custom Storage endpoints

Choose the request address style when constructing the signer. For example,
Azurite's Blob endpoint at
`http://127.0.0.1:10000/devstoreaccount1/container/blob` uses path-style addressing.

```rust
use reqsign::{azure, default_context};

let signer = azure::default_signer(default_context()).with_request_signer(
    azure::RequestSigner::new()
        .with_account_name("devstoreaccount1")
        .with_addressing_style(azure::AddressingStyle::PathStyle),
);
```

For a custom domain with URLs of the form `https://storage.example/container/blob`,
use the default host style. Set `with_account_name` to the storage account for
User Delegation SAS on either endpoint. Use `with_service_sas_permissions` with
a Shared Key credential, or `with_user_delegation_presign` with a bearer credential,
then pass the desired lifetime to `sign`. User Delegation presigning sends a key
request to the selected account root on the caller's endpoint.

## Table Storage Shared Key

Set `with_shared_key_mode(azure::SharedKeyMode::Table)` on the request signer
and call `sign` with `None` to sign a Table request with Shared Key. The default
Shared Key mode serves Blob, Queue, and File requests.
[Microsoft Learn](https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-shared-key#table-service-shared-key-authorization)

## Azure API keys

The `azure` feature also exposes `reqsign::azure::api_key` for Azure APIs that
accept a key in a request header. Assemble a `Signer` with a static key or a
caller-named environment variable and select the header required by the API.
When the key rotates, create a new signer or call `with_credential_provider`
with a provider for the rotated key. See the [signing example](https://docs.rs/reqsign/latest/reqsign/azure/index.html#azure-api-keys).

## Managed identity

The default chain's `imds` slot supports App Service, Functions, Container Apps,
and Azure VM IMDS. App Service, Functions, and Container Apps supply
`IDENTITY_ENDPOINT` and `IDENTITY_HEADER`. Legacy App Service and Functions supply
`MSI_ENDPOINT` and `MSI_SECRET`. Each protocol sends its own header to its configured
endpoint. Use `no_imds()` to remove this slot. See the [provider configuration](https://docs.rs/reqsign-azure-storage/latest/reqsign_azure_storage/struct.ImdsCredentialProvider.html).

## Client certificate authentication

On native targets, set `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, and
`AZURE_CLIENT_CERTIFICATE_PATH`. The PEM file must contain an unencrypted
PKCS#8 or PKCS#1 RSA private key and its certificate. Put the leaf certificate
first, followed by any issuer certificates in chain order.

For Microsoft Entra Subject Name/Issuer authentication, set
`AZURE_CLIENT_SEND_CERTIFICATE_CHAIN=true` to send the public certificates in
the assertion's `x5c` header. The header is omitted by default.
`ClientCertificateCredentialProvider::with_send_certificate_chain` overrides
the environment setting, including when set to `false`.
