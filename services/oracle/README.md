# reqsign-oracle

Oracle Cloud Infrastructure request signing implementation for reqsign.

The default credential provider checks OCI environment variables and then the
OCI configuration file at `~/.oci/config`. The config path and profile can be
selected with `OCI_CONFIG_FILE` and `OCI_PROFILE`.

## Quick Start

```rust,no_run
use reqsign_core::{Context, OsEnv, Signer};
use reqsign_file_read_tokio::TokioFileRead;
use reqsign_oracle::{DefaultCredentialProvider, RequestSigner};

let context = Context::new()
    .with_file_read(TokioFileRead)
    .with_env(OsEnv);

let signer = Signer::new(
    context,
    DefaultCredentialProvider::new(),
    RequestSigner::new(),
);
```

The environment provider reads `OCI_USER`, `OCI_TENANCY`, `OCI_KEY_FILE`, and
`OCI_FINGERPRINT`. Use `StaticCredentialProvider` or
`DefaultCredentialProvider::builder()` for explicit configuration.

## Configuration Profiles

Select a named profile with `OCI_PROFILE`. Missing credential fields in an existing
profile inherit from `[DEFAULT]`, following the OCI
[profiles and inheritance](https://docs.oracle.com/en-us/iaas/Content/API/Concepts/sdkconfig.htm)
convention:

```ini
[DEFAULT]
tenancy=ocid1.tenancy.oc1..example
user=ocid1.user.oc1..default
fingerprint=default-fingerprint
key_file=~/.oci/default.pem

[ADMIN]
user=ocid1.user.oc1..admin
fingerprint=admin-fingerprint
key_file=~/.oci/admin.pem
```

With `OCI_PROFILE=ADMIN`, the provider uses the admin user and key and inherits
the default tenancy. Explicit values, including empty values, override defaults.
A missing profile or a profile still missing required fields yields no credential;
the provider does not substitute another named profile.

Configuration values are literal. Write Windows paths such as
`C:\Users\example\.oci\api_key.pem` directly, without doubling backslashes or
adding surrounding quotes. If a config previously relied on INI escape processing,
replace the escaped value with the literal path. Home expansion of `~/` happens
after resolving the selected profile. Config files are reread when the provider
is invoked, so inherited values participate in credential refresh as well.

## Request Body Headers

OCI requires additional signed headers for requests that carry a body:

- `POST`, `PUT`, and `PATCH` requests must include `content-length`,
  `content-type`, and `x-content-sha256`.
- Object Storage `PutObject` and `UploadPart` `PUT` requests may omit these
  headers. If the request already contains any of them, reqsign includes it in
  the signature.

Reqsign signs the header values already present on the request. It does not
read the body, compute `x-content-sha256`, or infer the endpoint from the
request authority. Prepare the headers before calling `sign`:

- `content-length`: decimal number of body bytes. OCI requires `0` for an empty
  body on `POST` and `PUT` requests outside the Object Storage exception.
- `content-type`: the body media type.
- `x-content-sha256`: the base64-encoded SHA-256 digest of the body. For an
  empty body, this is `47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=`.

Set these headers on the request before calling `sign`. If the HTTP client adds
or replaces `content-length` or `content-type` after signing, the wire headers
no longer match the signed fields and the provider may reject the request.

`GET`, `HEAD`, and `DELETE` requests keep the bodyless contract and sign only
`date`, `(request-target)`, and `host`. Each signed body header must have exactly
one value; duplicate signed headers are rejected without changing the request.

Reqsign cannot compute the digest without access to the request body. A
body-aware signing API remains future work; callers must supply
`x-content-sha256` today.

## Private Key Formats

The file selected by `OCI_KEY_FILE` or the OCI configuration's `key_file` entry
may contain an unencrypted RSA private key in either format:

- PKCS#1 PEM, with the `BEGIN RSA PRIVATE KEY` label, as generated by older
  OpenSSL versions using `openssl genrsa`.
- PKCS#8 PEM, with the `BEGIN PRIVATE KEY` label.

Both formats work directly; existing PKCS#1 keys do not need conversion to
PKCS#8. Encrypted private keys and public key files are not supported.
